# Requirements Document

## Introduction

This document defines the requirements for a Customer Relationship Management (CRM) platform for an office rental company. The System manages office unit inventory and occupancy status, allots office units to Office Owners, provides a dedicated portal for Office Owners to manage their account and raise maintenance complaints, generates rent bills and invoices, collects rent payments through UPI and Razorpay, and sends payment reminders. The System also includes lease management, reporting, document storage, and role-based access to support the day-to-day operations of the rental company's administrative staff.

## Glossary

- **System**: The office rental CRM platform as a whole, including backend services and all user-facing portals.
- **Admin_Portal**: The interface used by Company_Staff to manage office units, allotments, billing, and complaints.
- **Owner_Portal**: The dedicated web/mobile interface used by an Office_Owner to view their account, pay rent, and raise complaints.
- **Company_Staff**: An employee of the office rental company who uses the Admin_Portal, including roles such as Administrator and Maintenance_Staff.
- **Administrator**: A Company_Staff member with full permissions to manage office units, owners, billing, and system configuration.
- **Maintenance_Staff**: A Company_Staff member responsible for resolving Maintenance_Complaints assigned to them.
- **Office_Owner**: An individual or business entity that has been allotted one or more Office_Units by the company under a lease and is billed for rent. This term refers to the tenant/occupant of an Office_Unit, not the owner of the building.
- **Office_Unit**: A physical, individually allottable office room or space managed by the System, identified by a unique unit code and belonging to a Building.
- **Building**: A physical property containing one or more Office_Units.
- **Occupancy_Status**: The state of an Office_Unit, either "Vacant" or "Occupied".
- **Allotment**: A record associating an Office_Unit with an Office_Owner for a defined lease period.
- **Lease**: A contractual agreement tied to an Allotment that defines the rent amount, billing cycle, start date, and end date.
- **Invoice**: A billing document generated by the System for a specific billing cycle, listing the rent amount and any additional charges due from an Office_Owner.
- **Payment**: A monetary transaction recorded against an Invoice, made via UPI or Razorpay.
- **Receipt**: A document generated by the System confirming a successfully completed Payment.
- **Payment_Gateway**: A third-party service (UPI or Razorpay) integrated with the System to process Payments.
- **Maintenance_Complaint**: A service request raised by an Office_Owner through the Owner_Portal describing a maintenance issue with their Office_Unit.
- **Reminder**: An automated notification sent to an Office_Owner regarding an upcoming or overdue rent Payment.
- **Notification**: Any automated message (email, SMS, or in-app) sent by the System to a User.
- **User**: Any Company_Staff member or Office_Owner who authenticates into the System.

## Requirements

### Requirement 1: Office Unit Registration and Listing

**User Story:** As an Administrator, I want to register and list all office units, so that I can maintain an accurate inventory of the company's rentable office space.

#### Acceptance Criteria

1. WHEN an Administrator submits a new Office_Unit with a unit code (1-50 characters), Building, floor (-5 to 200), size (greater than 0 and up to 1,000,000 square feet), and base rent amount (0.01 to 9,999,999.99), THE System SHALL create the Office_Unit record with an initial Occupancy_Status of "Vacant".
2. IF an Administrator submits a new Office_Unit with a unit code that already exists within the same Building, THEN THE System SHALL reject the submission and return a descriptive error.
3. WHEN an Administrator navigates to the Office_Unit list view, THE Admin_Portal SHALL display a list of all Office_Units showing unit code, Building, floor, size, base rent amount, and Occupancy_Status.
4. WHEN an Administrator applies a filter by Building, Occupancy_Status, or both, THE Admin_Portal SHALL display only the Office_Units matching all selected filter criteria, or an empty list with an indication that no Office_Units match if none qualify.
5. WHEN an Administrator updates the Building, floor, size, or base rent amount of an existing Office_Unit, THE System SHALL save the updated details and record the update timestamp, without changing the Office_Unit's Occupancy_Status.
6. IF an Administrator submits a new Office_Unit with a unit code, floor, size, or base rent amount outside the defined bounds, THEN THE System SHALL reject the submission and return a descriptive error.
7. IF an Administrator submits an update to an existing Office_Unit with a value outside the defined bounds or a unit code that duplicates another Office_Unit within the same Building, THEN THE System SHALL reject the update and return a descriptive error.

### Requirement 2: Office Occupancy Status Tracking

**User Story:** As an Administrator, I want to see which office units are occupied and which are free, so that I can quickly identify available inventory for new tenants.

#### Acceptance Criteria

1. WHEN an Allotment is created for an Office_Unit, THE System SHALL atomically set the Occupancy_Status of that Office_Unit to "Occupied" and activate the Allotment, such that neither change is saved unless both succeed.
2. WHEN an Allotment for an Office_Unit transitions to status "Terminated" or "Expired", THE System SHALL atomically update the Allotment status and set the Occupancy_Status of that Office_Unit to "Vacant", such that neither change is saved unless both succeed.
3. THE Admin_Portal SHALL display a summary count of Office_Units with Occupancy_Status "Occupied" and a summary count of Office_Units with Occupancy_Status "Vacant", together reflecting the total count of all Office_Units in the System.
4. IF an Administrator attempts to create an Allotment for an Office_Unit whose Occupancy_Status is "Occupied", THEN THE System SHALL reject the request, and no Allotment SHALL be created and no Occupancy_Status change SHALL occur.

### Requirement 3: Office Allotment Management

**User Story:** As an Administrator, I want to allot a vacant office unit to an office owner, so that the rental agreement and billing cycle can begin.

#### Acceptance Criteria

1. WHEN an Administrator creates an Allotment linking an Office_Owner to a vacant Office_Unit with a Lease start date, Lease end date, rent amount (greater than 0), and billing cycle, THE System SHALL create the Allotment with an initial status of "Active" and the associated Lease record.
2. THE System SHALL associate at most one Allotment with status "Active" with an Office_Unit at any given time.
3. WHEN an Administrator terminates an Allotment with status "Active" before its Lease end date, THE System SHALL record the termination date and set the Allotment status to "Terminated".
4. IF an Administrator attempts to terminate or expire an Allotment whose status is already "Terminated" or "Expired", THEN THE System SHALL reject the request, return a descriptive error, and leave the Allotment status unchanged.
5. WHEN a Lease end date is reached and no new Allotment with status "Active" has been created for the Office_Unit, THE System SHALL set the Allotment status to "Expired" and update the Occupancy_Status of the Office_Unit to "Vacant".
6. WHEN an Administrator expires an Allotment with status "Active" before its Lease end date due to non-payment or policy violation, THE System SHALL set the Allotment status to "Expired", record the expiration reason, and update the Occupancy_Status of the Office_Unit to "Vacant".
7. WHEN an Administrator manually forces the expiration of an Allotment whose Lease end date has passed but whose status has not yet been automatically updated, THE System SHALL set the Allotment status to "Expired" and update the Occupancy_Status of the Office_Unit to "Vacant".
8. THE Admin_Portal SHALL display the Allotment history for a given Office_Unit, including for each Allotment the Office_Owner, Lease start date, Lease end date, rent amount, and Allotment status.

### Requirement 4: Office Owner Account Management

**User Story:** As an Administrator, I want to create a dedicated account for each office owner, so that the owner can access their own portal to manage their rental.

#### Acceptance Criteria

1. WHEN an Administrator creates an Office_Owner account with a name (1-100 characters), contact email, phone number (10-15 digits), and password (minimum 8 characters), THE System SHALL create the account and send a Notification containing login instructions to the registered contact email.
2. IF an Administrator creates an Office_Owner account using a contact email that already exists in the System, THEN THE System SHALL reject the submission and return a descriptive error.
3. IF an Administrator submits an Office_Owner account creation request with an invalid email format, phone number outside the defined bounds, or password shorter than the minimum length, THEN THE System SHALL reject the submission and return a descriptive error.
4. THE System SHALL restrict an Office_Owner's Owner_Portal visibility to only their own Allotments, Invoices, Payments, and Maintenance_Complaints.
5. WHEN an Office_Owner updates their name, contact email, or phone number through the Owner_Portal, THE System SHALL validate the new values against the same format rules as account creation and save the updated information.
6. IF an Office_Owner submits a profile update with an invalid email format, phone number outside the defined bounds, or an email that already exists on another account, THEN THE System SHALL reject the update and return a descriptive error.
7. WHEN an Administrator deactivates an Office_Owner account, THE System SHALL terminate any active session for that account and prevent that account from authenticating into the Owner_Portal.
8. THE System SHALL prevent an Office_Owner from viewing the Allotments, Invoices, Payments, or Maintenance_Complaints belonging to any other Office_Owner.

### Requirement 5: Authentication and Role-Based Access Control

**User Story:** As a User, I want to securely log into the portal appropriate to my role, so that I can only access functionality relevant to my responsibilities.

#### Acceptance Criteria

1. WHEN a User submits valid credentials, THE System SHALL authenticate the User and grant access to the portal corresponding to their role.
2. IF a User submits invalid credentials, THEN THE System SHALL deny access and return a descriptive error without indicating whether the email or password was incorrect.
3. THE System SHALL restrict Administrator-only actions, including Office_Unit creation, Allotment management, and account creation, to Users with the Administrator role.
4. THE System SHALL restrict Maintenance_Complaint assignment and resolution actions to Users with the Administrator or Maintenance_Staff role.
5. IF a User attempts an action restricted to a role they do not hold, THEN THE System SHALL deny the action and return a descriptive error.
6. WHILE a User session has been inactive for longer than the configured session timeout, THE System SHALL require the User to re-authenticate before granting further access.
7. IF a User submits invalid credentials for the same account a number of consecutive times exceeding the configured lockout threshold, THEN THE System SHALL lock the account for the configured lockout duration and deny further authentication attempts on that account until it elapses.
8. THE Admin_Portal SHALL allow an Administrator to configure the session timeout, lockout threshold, and lockout duration.

### Requirement 6: Maintenance Complaint Submission

**User Story:** As an Office Owner, I want to raise a maintenance complaint from the portal, so that issues with my office unit are reported and resolved.

#### Acceptance Criteria

1. WHEN an Office_Owner submits a Maintenance_Complaint with a category selected from the System's configured list of Maintenance_Complaint categories, a description (1-2000 characters), and 0-5 optional attachments (each up to 10 MB, of a file type accepted by the System) for their allotted Office_Unit, THE System SHALL create the Maintenance_Complaint with status "Open".
2. THE Owner_Portal SHALL display the list of Maintenance_Complaints raised by the authenticated Office_Owner along with their current status ("Open", "Assigned", "In Progress", or "Resolved").
3. WHEN an Office_Owner views a submitted Maintenance_Complaint, THE Owner_Portal SHALL display the status history and any comments added by Company_Staff.
4. IF an Office_Owner attempts to submit a Maintenance_Complaint for an Office_Unit that is not currently allotted to them, THEN THE System SHALL reject the submission and return a descriptive error.
5. IF an Office_Owner submits a Maintenance_Complaint with a category not in the configured list, a description outside the defined length, or an attachment exceeding the count, size, or file type limits, THEN THE System SHALL reject the submission, return a descriptive error, and create no Maintenance_Complaint record.

### Requirement 7: Maintenance Complaint Tracking and Resolution

**User Story:** As a Maintenance Staff member, I want to track and resolve maintenance complaints, so that office owners' issues are addressed in a timely manner.

#### Acceptance Criteria

1. THE Admin_Portal SHALL display all Maintenance_Complaints with their category, associated Office_Unit, Office_Owner, status, and creation date.
2. WHEN an Administrator assigns a Maintenance_Complaint to a Maintenance_Staff member, THE System SHALL atomically update the Maintenance_Complaint status to "Assigned" and record the assignee, such that neither change is saved unless both succeed.
3. WHEN the assigned Maintenance_Staff member updates a Maintenance_Complaint status to "In Progress" or "Resolved", THE System SHALL record the status change, the acting User, and a timestamp.
4. WHEN a Maintenance_Complaint status is changed, THE System SHALL send a Notification to the Office_Owner who raised it.
5. WHEN a Company_Staff member (Administrator or Maintenance_Staff) adds a comment (up to 2000 characters) to a Maintenance_Complaint, THE System SHALL append the comment to the complaint's status history.
6. IF an Administrator attempts to assign a Maintenance_Complaint whose status is "Resolved", THEN THE System SHALL reject the assignment and return a descriptive error.
7. IF a Maintenance_Staff member who is not the assigned staff for a Maintenance_Complaint attempts to update its status, THEN THE System SHALL reject the update and return a descriptive error.

### Requirement 8: Rent Invoice Generation and Billing

**User Story:** As an Administrator, I want the system to generate rent invoices automatically, so that office owners receive accurate and timely bills.

#### Acceptance Criteria

1. WHEN a Lease's billing cycle date is reached, THE System SHALL generate an Invoice for the associated Office_Owner with an initial status of "Due", containing the rent amount, billing period, due date, and any additional charges.
2. THE System SHALL calculate the Invoice due date as the Lease billing cycle date plus the configured payment grace period.
3. THE Owner_Portal SHALL display all Invoices for the authenticated Office_Owner along with each Invoice's status ("Due", "Partially Paid", "Paid", or "Overdue").
4. WHILE an Invoice status is "Due" or "Partially Paid", IF the Invoice due date passes, THEN THE System SHALL update the Invoice status to "Overdue".
5. THE Admin_Portal SHALL display billing history and outstanding dues across all Office_Owners, with the ability to filter by Building, Office_Owner, or Invoice status.
6. IF an Invoice has already been generated for a Lease's billing cycle, THEN THE System SHALL NOT generate a duplicate Invoice for that same billing cycle.
7. IF a Lease's billing cycle date is reached while the associated Allotment status is "Terminated" or "Expired", THEN THE System SHALL NOT generate an Invoice for that billing cycle.

### Requirement 9: Rent Payment Collection via UPI and Razorpay

**User Story:** As an Office Owner, I want to pay my rent online via UPI or Razorpay, so that I can settle my dues without visiting the office in person.

#### Acceptance Criteria

1. WHEN an Office_Owner initiates a Payment for an Invoice through the Owner_Portal, THE System SHALL present UPI and Razorpay as available Payment_Gateway options and require a Payment amount between 0.01 and the Invoice's outstanding due amount.
2. WHEN a Payment is completed successfully through a Payment_Gateway, THE System SHALL record the Payment against the associated Invoice and update the Invoice status to "Paid" if the total amount received equals or exceeds the Invoice amount, or "Partially Paid" if the total amount received is less than the Invoice amount.
3. IF a Payment attempt through a Payment_Gateway fails or is cancelled, THEN THE System SHALL record the failed attempt, send a Notification to the Office_Owner indicating the failure, and leave the associated Invoice status unchanged.
4. THE System SHALL record, for each Payment, the Payment_Gateway used, transaction reference identifier, amount, and completion timestamp.
5. WHEN a Payment_Gateway sends a payment confirmation callback, THE System SHALL verify the callback authenticity before updating the Invoice and Payment records.
6. IF an Office_Owner attempts to initiate a Payment for an Invoice whose status is already "Paid", THEN THE System SHALL reject the request and return a descriptive error.
7. IF the callback authenticity verification in criterion 5 fails, THEN THE System SHALL reject the callback, leave the Invoice and Payment records unchanged, and record the verification failure.
8. IF a Payment_Gateway sends a confirmed payment callback with a transaction reference identifier that has already been recorded as a completed Payment, THEN THE System SHALL discard the duplicate callback without creating a new Payment record or re-triggering the Invoice status update.

### Requirement 10: Payment Receipt Generation

**User Story:** As an Office Owner, I want to receive a receipt after paying rent, so that I have proof of payment for my records.

#### Acceptance Criteria

1. WHEN a Payment is successfully recorded against an Invoice, THE System SHALL generate a Receipt containing the Office_Owner name, Office_Unit, Invoice period, Payment completion timestamp, amount paid, Payment_Gateway, and transaction reference identifier.
2. THE Owner_Portal SHALL allow an Office_Owner to download the Receipt for any of their completed Payments immediately upon Receipt generation, regardless of the delivery status of any associated Notification.
3. WHEN a Receipt is generated, THE System SHALL send a Notification containing the Receipt to the Office_Owner's registered contact email.
4. IF the Notification containing the Receipt fails to deliver, THEN THE System SHALL retry delivery according to the configured retry policy, and THE System SHALL record the delivery failure once the configured retry policy is exhausted.
5. IF an Office_Owner attempts to download a Receipt for a Payment that does not belong to them or has no associated completed Payment, THEN THE Owner_Portal SHALL deny the request and return a descriptive error.

### Requirement 11: Rent Payment Reminders

**User Story:** As an Office Owner, I want to receive reminders about upcoming or overdue rent, so that I do not miss a payment deadline.

#### Acceptance Criteria

1. WHILE an Invoice status is "Due" or "Partially Paid" and the due date is within the configured reminder lead time, THE System SHALL send a Reminder Notification to the associated Office_Owner at the configured reminder frequency until the due date passes or the Invoice status becomes "Paid".
2. WHEN an Invoice status changes to "Overdue", THE System SHALL send a Reminder Notification to the associated Office_Owner indicating the overdue amount.
3. THE System SHALL send Reminder Notifications through the Office_Owner's registered email and, WHERE a phone number is available, through SMS.
4. IF an Invoice status changes to "Paid", THEN THE System SHALL stop sending further Reminder Notifications for that Invoice.
5. BEFORE sending any Reminder Notification, THE System SHALL verify the current Invoice status and SHALL NOT send the Reminder Notification if the Invoice status is "Paid".
6. THE Admin_Portal SHALL allow an Administrator to configure the reminder lead time and reminder frequency, each specified as a positive whole number of days.
7. WHILE an Invoice status is "Overdue", THE System SHALL send a Reminder Notification to the associated Office_Owner at the configured reminder frequency until the Invoice status becomes "Paid".
8. IF a Reminder Notification fails to deliver, THEN THE System SHALL retry delivery according to the configured retry policy and record the delivery failure once the retry policy is exhausted.
9. IF an Administrator configures a reminder lead time or reminder frequency that is not a positive whole number of days, THEN THE System SHALL reject the configuration and return a descriptive error.

### Requirement 12: Admin Dashboard and Reporting

**User Story:** As an Administrator, I want a dashboard summarizing occupancy and revenue, so that I can monitor business performance at a glance.

#### Acceptance Criteria

1. THE Admin_Portal SHALL display a dashboard showing total Office_Units, occupied count, vacant count, and current occupancy rate, calculated as the occupied count divided by the total Office_Unit count and rounded to the nearest whole percentage.
2. THE Admin_Portal SHALL display a dashboard summary of total rent collected, total outstanding dues, and overdue Invoice count for a selectable date range, defaulting to the current calendar month when no range is selected.
3. WHEN an Administrator selects a Building filter on the dashboard, THE Admin_Portal SHALL recalculate and display the occupancy and revenue figures for that Building only.
4. WHEN an Administrator clears the Building filter, THE Admin_Portal SHALL recalculate and display the occupancy and revenue figures across all Buildings.
5. THE Admin_Portal SHALL allow an Administrator to export billing and occupancy reports, reflecting the currently selected date range and Building filter, in CSV or PDF format.
6. IF an Administrator selects a date range whose start date is after its end date, THEN THE System SHALL reject the selection and return a descriptive error.

### Requirement 13: Lease Document and Record Storage

**User Story:** As an Administrator, I want to store lease agreements and related documents, so that important records are accessible when needed.

#### Acceptance Criteria

1. WHEN an Administrator uploads a document associated with a Lease or Office_Owner, THE System SHALL store the document and link it to the corresponding Lease or Office_Owner record.
2. THE Admin_Portal SHALL allow an Administrator to view and download documents linked to a Lease or Office_Owner.
3. THE Owner_Portal SHALL allow an Office_Owner to view and download documents linked to their own Lease or Office_Owner account.
4. THE System SHALL maintain a configurable file_type_accepted flag per file type and a configurable maximum file size in megabytes.
5. IF an uploaded document exceeds the configured maximum file size or has a file type for which file_type_accepted is not set, THEN THE System SHALL reject the upload, return a descriptive error, and SHALL NOT store the document.
6. IF an Office_Owner attempts to view or download a document linked to another Office_Owner's Lease or account, THEN THE System SHALL deny the request and return a descriptive error.

### Requirement 14: Audit Logging

**User Story:** As an Administrator, I want key actions in the system to be logged, so that I can review changes to allotments, billing, and accounts if a dispute arises.

#### Acceptance Criteria

1. WHEN an Allotment, Invoice, Payment, or Office_Owner account is created, modified, or terminated, THE System SHALL record an audit log entry containing the acting User, action type, the affected record's unique identifier, a timestamp, and, for modifications, the changed field name, previous value, and new value.
2. THE Admin_Portal SHALL allow an Administrator to view the audit log filtered by User, action type, or date range, displaying for each entry the acting User, action type, affected record identifier, and timestamp.
3. THE System SHALL NOT permit any User to modify or delete an existing audit log entry.
4. IF recording an audit log entry for an action fails, THEN THE System SHALL NOT commit that action and SHALL return a descriptive error.
